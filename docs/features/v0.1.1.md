# v0.1.1 — Visible `/workflow` sessions

## FEATURE_002: Visible workflow handoff and session title integration

### Problem

Free-text `/workflow` commands previously wrapped both the user's query and internal authoring instructions in a plugin `relay` message. DSH correctly treated that message as injected context: it collapsed the row in chat and excluded it from session-title generation. The Session was already attached to its Workspace, but its title projection remained `null`; in DSH Web's manual-order view, groups with more than five sessions could therefore hide the generic fallback row under “expand remaining”.

### Resolution

- Deliver the exact trimmed query as a `source.kind: user` message through the Agent's normal steering boundary.
- Deliver the workflow authoring contract separately through `agent.inject()` as `@dsh-external/workflow` relay context.
- Bind the one-shot generated-workflow approval grant to the exact user-message id; later human input, another turn, forged plugin context, and repeated tool calls remain fail-closed.
- Verify with the real DSH `SessionStore`, `CommandRuntime`, and `SessionTitleService` composition that the query is eligible for deterministic fallback and model-backed title providers.
- Document DSH Web's five-row manual-order collapse and the “Last updated” alternative; Workspace membership was already correct and no browser-private storage is mutated by the Host plugin.

### Acceptance

- `/workflow <query>` returns from the command plane immediately.
- Chat receives one visible human message containing only `<query>`.
- Internal authoring guidance remains a separate plugin context message.
- A title is derived from `<query>` and published through DSH's native title projection.
- Inline execution receives exactly one explicit-intent grant for the corresponding message.
- Full unit/integration suite, typecheck, build, package and current DSH compatibility checks pass.
